1. 이 맵이 하는 일

「99년도 영원히 갇힌사람 · v1.1.6」은 6명이 역할을 받아 탐색하고, 차례대로 주남희에게 질문하며, 유닛 변신과 단계별 사건을 거쳐 고정 서사·에필로그를 보는 맵이다. 질문을 외부 처리기에 전달하는 메모리 프로토콜, 작은 영상판, 한글 음절 음성 재생기가 게임 로직과 함께 들어 있다.

실제 사건을 설명하는 고정 대사는 맵 안에 저장되어 있다. 이 보고서에서 역사 관련 문장은 맵이 그렇게 출력하도록 작성되어 있다는 뜻이며, 해당 사건의 사실관계를 별도로 검증한 역사 보고서는 아니다.

질문현재 차례·턴 세대·참가 상태·접두사 4 등을 검사하고 플레이어별 요청 칸에 기록한다.
주요 사건P8 미네랄 2,000을 기점으로 세 종류의 적 NPC와 지역/변신 조건을 처리한다.
서사주 단계 6~9에서 탈출 질문 문구를 최대 5회 출력하고, 주 단계 9에서 사건 기록을 자동 진행한다.
에필로그사건 기록 마지막 대사 후 별도의 연출 상태기계가 시작된다. 동쪽 표식으로 후속 대사 일부를 다시 들을 수 있다.
외부 연동8 KiB 메모리 영역과 동기화 패킷을 통해 질문·응답·미디어를 교환한다. 외부 GPT 프로그램 자체는 첨부되지 않았다.

분석 범위: 첨부된 두 EPS 전체를 읽고 구조를 인덱싱했다. 원본 SCX/SCM, 음원 파일, 외부 처리기는 포함되어 있지 않다. 실제 StarCraft를 실행한 결과는 아니며, 지원되는 EUD 명령만 다루는 제한적 검산과 정적 추적을 함께 사용했다.

파일은 원래 함수의 실행 순서대로 정렬된 소스가 아니다. R_... 별칭과 S_component_... 객체를 선언한 다음, 각 노드의 nextptr와 이를 다시 쓰는 액션으로 실행을 연결한다. 따라서 파일에서 앞뒤에 놓인 두 블록이 게임에서도 연속 실행된다고 보면 안 된다. R_1000070 같은 이름은 복원된 주소 별칭이며 그대로 실제 절대 메모리 주소 0x1000070이라고 읽지 않았다. S_component_... + n은 그 객체에서의 바이트 오프셋이다.

공유 변수 영역의 많은 노드는 72바이트 간격으로 겹쳐 배치된 단일 액션 트리거다. 읽기·쓰기·변수 복사·함수 인자 전달·반환·조건 점프가 이런 노드로 확장되어 있어 줄 수가 커진다. 이 구조 때문에 게임 규칙뿐 아니라 화면 출력, 문자열 처리, 패킷 처리에 사용되는 기반 코드가 많이 보인다.

텍스트 인코딩도 혼합되어 있다. 기존 안내와 역할은 CP949, 확장 UI와 긴 대사는 UTF-8이 주로 사용된다. 복호화된 HUD 문구 116개는 서로 다른 문구 34개를 여러 호출 지점에 펼친 형태이며, 대부분의 사건 서사는 이 ENC 상수가 아니라 숫자 데이터 안에 저장되어 있다.

6. 이름표·아이템·변신 알림

7. 탈출 질문과 사건 기록은 조건에 따라 자동 진행한다

유효한 질문을 수락한 뒤 이에 대응하는 응답을 넣으면 “주남희:” 접두사와 TEXT_3287 버퍼를 구성하는 출력 경로에 들어간다. 암호화 문자열용 재구성 런타임이 첨부되지 않아 이 검산에서 실제 화면의 완성 문장까지 재현하지는 않았다. 문자열 포인터와 출력 호출을 연결한 정적 근거로 응답 표시 용도를 확인했다.

type 2의 mode 1에는 대사 외에 opcode 1~25의 명령 데이터를 수락하는 경로가 있다. unit ID 0~227 또는 특수값 1000~1004, 좌표 상한 4095, 수량 1~30 등의 공통 검증과 opcode별 인자 그룹 검사가 보인다. 검증 후 component_34953에서 opcode를 opaque+18511704의 배열에 저장하며, unit 등 나머지 값도 병렬 배열에 넣는다. 소비 경로 component_6106 → component_22867은 opcode, unit, x, y, 수량, mode, 두 번째 unit, value, 추가 인수의 아홉 값을 읽는다.

따라서 외부 응답 채널에 텍스트 외의 명령 큐가 존재한다는 것은 확인됐다. 다만 opcode 1~25 전체의 최종 효과를 각각 이름에 대응시키지는 못했다. 검증기의 enum 비교를 실제 효과 디스패치로 오인하지 않도록 미확정으로 남겼다.

명령 데이터의 바이트 배치는 +16 opcode, +20 unit, +24 x, +28 y, +32 수량, +40 mode, +44 두 번째 unit, +48 value, +52 추가 인수로 확인했다. +36은 공통 헤더의 textByteLen 자리다. 입력 길이가 40·48·52·56바이트일 때 선택 인수를 순서대로 읽으며, 없는 값은 mode=0, 두 번째 unit=228, value=0, 추가 인수=0으로 초기화한다. 이 필드명은 읽는 방식에 붙인 설명 이름이며 모든 opcode에서 같은 의미로 사용된다고 단정하지 않았다.

실제 메모리 효과까지 확인한 예는 opcode 14의 생산 큐 항목 제거다. opcode=14, unit=0(Marine), 수량=1을 검증기에서 수락한 뒤 큐에 넣고 소비하도록 했다. P8 Barracks에 Marine 생산 큐 하나가 있다고 가정한 CUnit 메모리를 제공하자, component_14518(S 365,383행)의 +0x98 생산 큐 처리와 component_43951(S 748,057행)의 228(None) 값을 거쳐 component_15113(S 371,558행)가 첫 생산 항목을 0에서 228로 비웠다. CUnit의 +0x98이 5개의 16비트 생산 큐 슬롯이라는 구조는 BWAPI CUnit.h와도 대조했다. 외부 응답이 실제 게임 유닛 구조를 수정하는 기능을 포함한다는 구체적인 예다. 생산 비용 환불이나 모든 명령의 최종 효과까지 확인한 결과는 아니다.

opcode 1은 생산 요청에 연결된다. Marine(unit 0) 생산 요청을 검증기에서 수락한 뒤, P8 Barracks의 생산 큐가 모두 228(None)인 합성 상태를 넣었다. 같은 component_15113이 첫 슬롯을 228에서 0(Marine)으로 바꾸었고, component_34431은 유닛 구조 +0xA6의 secondaryOrder 값을 0x26으로 설정했다. 따라서 외부 명령의 대표 두 기능으로 opcode 1의 생산 요청, opcode 14의 생산 큐 항목 제거를 구별할 수 있다. 이 검산은 큐와 명령 필드의 전이까지 확인한 것이며 실제 생산 완료·비용 처리·게임 실행 전체를 재현한 것은 아니다.

질문 레코드를 기록할 때는 +0의 요청 시퀀스를 먼저 0으로 만들고 내용·추적값을 작성한 뒤, 마지막에 새 시퀀스를 +0에 넣어 완료를 표시한다. 외부 처리기는 질문 문자열만 보는 것이 아니라 이 완료 표시와 요청 시퀀스를 함께 읽도록 설계되어 있다.

외부 GPT 처리기의 실제 코드·모델·프롬프트·API 주소는 이 두 EPS에 없다. 확인된 것은 질문을 기록하고 응답 및 미디어 패킷을 처리하는 맵 쪽 계약이다. 이름에 GPT가 있다는 이유로 고정 사건 대사까지 모두 실시간 생성이라고 해석할 수 없고, 이 파일만으로 외부 서비스가 현재 정상 응답한다고 검증할 수도 없다.

10. 작은 영상판과 한글 음절 음성

영상 관련 데이터에는 SC_MINIMAP_BOARD_V3 식별자가 있고, component_24221(S 468,578행)의 공유 설정에는 32,32,256,2가 들어 있다. 맵 설명의 32×32·4색 압축 영상과 일치하는 구조다. 32×32 픽셀을 픽셀당 2비트로 표현하면 256바이트라는 관계도 맞는다.

입력 control DWORD의 상위 2비트를 mode로, 하위 30비트를 sequence로 분리한다(component_10239, S 320,178행 / component_29779, S 596,327행). 여러 mode 분기 가운데 mode 0의 전체 프레임 디코더에서 raw와 PackBits RLE 두 경로를 확인했다. 다른 mode의 의미를 모두 복원한 것은 아니다.

입력 영역 opaque+13928724에서 16비트 압축 길이를 읽고, 바로 뒤의 1바이트 codec과 payload를 처리한다. codec 0은 256바이트 원본 경로, codec 1은 PackBits식 반복/리터럴 복원 경로다. 복원 결과는 opaque+12897064에 놓인다. component_33251(S 634,008행) 및 component_27311(S 501,687행)에서 시작하는 처리를 확인했다.

검산 예시는 압축 입력 81 55 81 AA 4바이트다. 이를 0x55 128개와 0xAA 128개, 합계 정확히 256바이트로 풀었고 성공 플래그가 세워졌다. 불충분한 입력 00 55는 성공 처리되지 않았다. 이후 component_7127에서 이어지는 경로가 2비트 그룹을 lookup(opaque+5852968)으로 재배열하여 opaque+8161296의 64 DWORD 프레임 버퍼에 쓴다. 위 입력에서는 0x55555555 32개와 0xAAAAAAAA 32개를 확인했다. 실제 클라이언트의 최종 픽셀 표시·색상·FPS는 검증하지 않았다.

음성은 v\XXXX.wav 파일명 3,192개와 sequel\residual_thought.wav를 참조한다. 앞의 3,192개는 긴 대사를 각각 녹음한 목록으로 보기 어렵다. 파일명의 16진수 값에 0xAC00을 더하면 한글 음절이 되고, 목록은 초성·중성 399조합에 제한된 종성 변형을 배치한 패턴이다. 예를 들어 v\0000.wav는 “가”에 해당하는 코드다.

런타임에는 한글 음절 인덱스 상한 0x2BA3(11,171) 검사와 동적 PlayWAV 호출이 있다. component_30129(S 600,026행) 및 component_14011(S 360,012행)를 참고하면 된다. 재생할 WAV ID는 component_5420(S 268,983행)에서 액션 필드를 바꿔 넣는다. 정적인 PlayWAV 호출 component_37382(S 677,809행)는 sequel\residual_thought.wav를 가리킨다.

수신 type 4 패킷은 음절 음성 패킷으로 연결된다. 5개의 DWORD 헤더(20바이트) 뒤에 음절 번호를 2바이트씩 붙이며, mode 1, 음절 수 1~80, 전체 길이 20+2×음절 수라는 검사가 있다. 각 번호는 0~11,171 범위인지 확인한다. component_15683(S 377,605행), component_45586(S 765,435행)이 이 검사에 포함된다. 현재 음성/요청 식별값과 맞는 패킷이 수락되면 큐 수와 재생 상태가 갱신된다.

음절 번호는 한글 코드포인트에서 0xAC00을 뺀 값이며, 맵은 이를 제한된 음원 목록에 대응시킨다. component_30129부터 시작하는 루틴을 평가하면 code 0은 WAV ID 93(가), code 1은 ID 94(각), code 2(갂)도 ID 94(각)로 간다. code 4는 ID 95(간), code 28은 ID 101(개), code 0x101F는 ID 1275(밟), code 11,171은 ID 3280으로 연결된다. 따라서 모든 한글 음절마다 별도 녹음이 있는 구조는 아니며 일부 종성을 대체해 재생한다.

파일명 목록은 19×21×8=3,192개의 음절 변형을 이루며, 종성 나머지 값은 대체로 0,1,4,7,8,10,14,21이다. 단 하나의 예외 파일명 v\101f.wav는 “밟”에 해당한다. 확인한 맵 쪽 음성 처리는 음절 음원을 선택해 PlayWAV를 연속 호출하는 방식이다. 외부 처리기에서 추가 합성·정규화를 하는지는 그 코드가 없어 확인하지 못했다.

type 4의 mode 2는 음성 큐 취소에 연결된다. 전체 길이 20바이트, 옵션과 음절 수가 0인 제어 입력에서는 component_38004(S 684,368행)를 거쳐 큐 수가 0으로 줄고 재생 인덱스들이 초기화되며 상태가 5로 바뀌는 것을 확인했다.

첨부된 EPS에는 WAV 경로가 있으며, 음원 데이터 자체는 없다. 따라서 여성 목소리인지, 실제 발음·자연스러움·누락 음절·음질이 어떤지 청취 검증한 결과는 아니다. 설명 문자열에 있는 “여성 음성 재생 개선”과 실제 음원 품질은 구분했다.

12. RawTrigger를 실제 의미로 읽는 방법

이 맵에서는 Deaths/SetDeaths가 전투 중 사망한 유닛을 세는 기능과 변수·메모리 접근 양쪽에 사용된다. 일반적인 논리 주소 계산은 0x58A364 + player×4 + unit×48이며, EPD(address)로 만든 플레이어 인수를 사용하면 특정 DWORD를 읽고 쓸 수 있다. 아래의 고정 주소는 EPS가 쓰는 EUD 주소 기준이다.

패턴의미
